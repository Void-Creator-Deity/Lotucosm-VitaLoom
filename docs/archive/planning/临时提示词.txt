  二、发行打包策略：从基础架构开始
  你的“整个从基础架构开始打包”可以按以下四个层级组织成最终的安装包/发行版：

  1. 基础安装器（Bootstrap Installer）
  内容：

  Python 嵌入式运行环境（或引导用户安装指定 Python 版本）

  L0 Shell (core/shell)

  L1 核心插件（如崩溃上报、日志）

  一个最小的启动器 vitalloom.exe (PyInstaller 生成)，入口为 main.py

  职责：

  启动后只加载 L1 插件，维持基本运行环境

  内置“产品宿主管理器”（可以是极简的本地插件下载器）

  默认不包含任何 L2 产品宿主

  发行形态：一个 30–50MB 的基础包，像 VS Code 的骨架。

  2. 产品宿主（L2 大插件）的分发方式
  有两种策略，取决于你希望用户如何获取：

  策略 A：内置宿主（推荐初期）

  把 L2 插件 lotucosm.vitaloom.product 直接打包进基础安装器的 plugins/ 目录。

  启动时，Shell 自动加载，直接进入 Hub 界面。

  用户感觉“即装即用”，类似大多数编辑器。

  策略 B：按需下载（长期）

  基础安装器只带一个“产品市场”或“Hub 引导程序”。

  首次启动时让用户选择安装哪些产品宿主（如“织机编辑器”、“纯运行时播放器”）。

  L2 插件可通过在线包管理下载到 plugins/。

  无论哪种，L2 作为一个大插件，必须保持独立目录，版本号在 plugin.json 中管理，方便更新。

  3. 织机扩展（L3）的打包
  内置扩展：editor_essentials、engine.sr2d 等可随 L2 插件一起分发，放在 L2 目录下的 builtin_extensions/。

  社区扩展：通过 L2 的 PackageManagerPlugin（LoomPluginLoader）从线上仓库安装，放到用户目录的 extensions/（如 %APPDATA%/VitaLoom/extensions）。

  扩展的依赖（如 PyPI 包）可使用虚拟环境或嵌入 pip 在激活时安装，类似 Blender 插件。

  关键：L3 扩展绝不能直接放到 Shell 的 plugins/ 目录，必须由 L2 管理其生命周期和隔离环境。

  4. 工程（L4）只是数据
  工程文件是用户的文档，不属于发行包。

  工程插件 (addons/) 是工程的一部分，跟随工程版本控制。

  可以提供一个“工程模板”打包，方便新建项目。

  三、具体打包技术栈建议
  可执行文件生成
  使用 PyInstaller 打包 main.py 为 FrameCore.exe（或平台对应格式）。

  把 core/、plugins/（L1）和 Python 标准库一起打包成一个目录或单文件。

  处理动态加载：

  PyInstaller 打包后，Python 脚本会被冻结，但你的插件需要能够 .py 或 .zip 动态加载。因此：

  确保 PluginRegistry 使用 importlib 或 zipimport，并且插件目录不被 PyInstaller 打包进 exe，而是作为外部文件夹。

  推荐布局：

  text
  /VitaLoom/
      FrameCore.exe           # PyInstaller 引导程序
      _internal/             # Python 运行时和冻结的模块
      plugins/               # L1/L2 插件放在这里（可写）
      extensions/            # L3 扩展（由 L2 管理）
  这样你的更新器可以只替换 plugins/ 中的特定插件目录，无需重装整个 exe。

  跨平台
  基础 Shell 和运行时（lotucosm）无 Qt，可直接跨平台，注意路径处理。

  织机会话依赖 PyQt，针对每个平台打包相应的 Qt 库（使用 PyInstaller 的 --add-binary）。

  自动更新
  L1 插件“自动更新”可以替换 Shell 自己的插件，但要更新 exe 本身推荐使用类似 Squirrel 或 Sparkle 的框架，或者简单的替换+重启。

  L2 和 L3 的更新可以热替换：下载新版到临时目录，下次启动时由 Shell 检查并移动。

  四、发行时的一个常见问题：版本兼容
  你的 project.json 中 required_packages 指定了 L3 扩展版本。如果某个工程需要 engine.sr2d >= 1.2，而用户安装的是 1.1，需要处理。

  可以在 L2 的工程加载时检查，并提示从包管理安装。

  更好的做法：允许同一扩展的多个版本共存。在 extensions/ 下以版本号命名目录，加载时根据 project.json 选择适当版本。你的架构中扩展注册表可以支持这一点。

  一、更新包的设计：L2 作为独立可替换模块
  因为你的 L2（lotucosm.vitaloom.product）本身就是一个 符合 Shell 插件接口的目录，更新时只需要替换这个目录或其中的文件。

  1. 更新包的形态
  建议发布为 .zip 或 .tar.gz，内部结构直接是插件的完整内容：

  text
  lotucosm.vitaloom.product/
  ├── plugin.json          # version: "1.3.0"
  ├── hub/
  ├── lotucosm/
  ├── vitaloom/
  ├── package_index/
  └── ...
  更新时：

  下载此包

  校验 hash

  解压到 plugins/ 目录下，覆盖旧版本

  下一次启动 Shell 会加载新版

  2. 最小化更新（增量 / 热更新）
  如果你希望更新包更小，可以把增量做成 补丁包（基于 diff 或 bsdiff），里面包含变更文件与一个 patch_manifest.json，更新器据此替换文件。
  但初期完全可以先用全量覆盖，可靠性高，实现简单。

  3. 多版本并存与回滚
  架构上可以支持版本化目录：

  text
  plugins/
     lotucosm.vitaloom.product-1.2.0/
     lotucosm.vitaloom.product-1.3.0/
     lotucosm.vitaloom.product -> lotucosm.vitaloom.product-1.3.0/   # 符号链接或指针
  Shell 的 PluginRegistry 加载时读取版本号，更新时下载新版本目录，然后修改符号链接或配置文件，下次启动生效。
  回滚只需改回指向旧版本。这完全不影响 Shell 自身，也不影响其他插件。

  二、自动更新放在哪一层？怎么实现？
  原则：更新器本身应该是 L1（或 L0 的基础服务）的职责，因为更新可能涉及 Shell 自身、L1 插件，以及 L2。
  但“只更新 L2”是这个更新器的一种使用场景。

  推荐方案：L1 增加一个 auto_updater 插件
  它由 Shell 在早期启动（在 L2 启动前或后都可以，取决于更新时机）。

  提供通用接口：查询注册表里的插件，对比远程版本，下载、校验、解压。

  它不依赖任何 L2 的具体模块，只依赖 PluginRegistry 的元数据（id、version）。

  对 L2 的更新就是一次普通的“插件更新”，和将来更新 L1 其他插件完全复用同一套逻辑。

  自动更新的流程（不破坏架构）
  Shell 启动 → 加载 L1 插件（包括 auto_updater）。

  auto_updater 读 plugins/ 下所有 plugin.json，得到 L2 的 id 与 version。

  向远程更新服务器查询该 id 的最新版本。

  若发现更新，下载新版本插件目录到临时位置。

  关键步骤：此时可以选择 立即替换（重启后生效） 或 后台静默安装，下次启动生效。
  更新器绝不在 L2 运行时直接覆盖其正在使用的文件，避免锁定问题。

  下次 Shell 启动时，PluginRegistry 加载到新的 L2 目录，架构不变。

  为什么不会破坏架构？
  边界清晰：更新器只操作文件系统（替换 L2 的目录），不调用 L2 的任何内部接口。

  生命周期隔离：更新发生在“运行时之前”（安装阶段），L2 的 on_load 是在加载新版本后才执行，旧版本不会与新版本互相干扰。

  扩展兼容性由 L2 自己负责：如果 L2 新版引入了插件 API 变更，L2 自己可以在 on_load 时做 L3 扩展的兼容检查。Shell 对此毫无感知。

  即使用户从旧工程切换到新 L2：工程内的 project.json 只声明依赖的 L3 扩展版本，L2 负责加载它们，不涉及 Shell。

  三、这种更新机制反而强化了架构
  你现在的分层让更新变成了简单的文件替换，没有连环爆炸的危险。
  对比一下单体架构：更新编辑器功能可能要重装整个程序，而你的用户只需要在线获取一个几 MB 的 L2 压缩包，重启就完成升级。
  核心 Shell 和 L1 插件（崩溃上报、日志）不受任何影响，保证了基础框架的稳定。

  额外的好处
  灰度发布：可以在 L2 发布时带上 beta 频道，让愿意尝鲜的用户手动切换版本目录。

  工程安全性：L4 工程文件绝不参与更新，不会因为升级而损坏用户数据。

  依赖轻量：更新器不需要庞大的框架，用 Python 标准库（zipfile, hashlib, urllib）就能完成，适合嵌入 L1。

  结论：把你的更新目标定位为“只更新莲池织机插件”不仅完全可行，而且正是你微内核架构最合理的用法。自动更新只需做成一个位于 L1 的通用插件更新器，它只碰 L2 的文件，不越界调用内部
  API，结构会被保护得很好。

  极简内核：L0 不包含任何业务，只负责插件登记、生命周期、会话上下文。

  产品作为插件：编辑器、运行时宿主（L2）是符合 Shell 插件接口的“大插件”，可独立更新。

  依赖反转：所有上层依赖抽象接口，L4 → L3 → L2 → L0，无逆向引用。

  六边形划分：领域核心（lotucosm）与 UI（vitaloom）分离，前者可无头运行。

  更新解耦：更新器只操作文件，不侵入插件运行时，支持只更新 L2 而不动内核。

  二、分层架构详述
  L0 · Shell（微内核）
  位置：core/shell/
  唯一入口：main.py，它只初始化 Shell，不创建任何业务对象。
  职责：

  PluginRegistry：管理所有已安装插件的元信息（id, version, dependencies, provides, 入口模块）。

  LifecycleRunner：根据依赖拓扑排序，执行 on_load(api) / on_unload()。

  Session：全局环境句柄，仅存放真正的全局状态：当前工程路径、用户标识、事件总线实例。

  IShell 接口：暴露给所有插件的 Shell 服务（日志器、事件发送、配置读写），所有业务必须通过此接口与 Shell 交互。

  优化点：

  Session 中不放置 UI 状态，避免 L2 内部 UI 事件污染 Shell。

  L1/L2 插件通过 IShell 获取总线，总线只传递跨产品通用事件（如工程切换、主题变更）。

  L1 · Shell 插件（基础服务）
  位置：plugins/shell/
  特征：可选、极少，只放与具体产品无关的基础设施。
  预置：

  crash_reporter：启动早期载入，捕获全局异常。

  logger_core：统一日志记录，输出到文件和控制台。

  auto_updater：通用插件更新器，不包含任何业务逻辑。

  auto_updater 关键设计：

  读取 plugins/ 下所有 plugin.json，对比远程清单。

  下载新版本到 plugins/.cache/，校验后覆盖或创建版本目录。

  绝不操作 L2 内部模块，只负责文件替换，下次启动生效。

  更新 L2 时，因为 L2 是标准插件，更新流程与更新 L1 其他插件完全一致。

  L2 · 莲池织机产品宿主（核心大插件）
  插件 ID：lotucosm.vitaloom.product
  位置：plugins/lotucosm.vitaloom.product/
  角色：它既是编辑器宿主，也是运行时宿主，实现 IProductHost 接口，由 Shell 加载。

  内部模块：

  text
  ├─ hub/                     # 工程中心（工程列表、新建、版本展示）
  ├─ lotucosm/                # 莲池运行时（Cosmos, Pond, tick）【纯 Python，无 UI】
  ├─ vitaloom/                # 织机会话（EditorKernel, PlayerShell, ProjectManager）【依赖 PyQt】
  ├─ package_index/           # 织机扩展注册表
  ├─ loom_plugin_loader.py    # L3 扩展加载器（只管理织机扩展）
  └─ product_manifest.json    # 产品元数据
  关键边界：

  lotucosm 可独立 import，通过接口与 vitaloom 通信，支持无头模式。

  vitaloom 是 UI 适配器，创建主窗口后通过 IShell 注册到 Shell 的窗口管理器。

  L2 拥有自己的内部事件总线，只在需要全局协同（如工程切换）时才与 L0 总线交互。

  与 Shell 的握手协议：

  L2 的入口类实现 IProductHost：

  on_load(shell: IShell)：创建主窗口并注册给 Shell。

  on_unload()：清理 UI，保存状态。

  Shell 通过 IShell.register_main_window(window) 接管窗口关闭/托盘控制。

  L3 · 织机扩展插件
  位置：extensions/（由 L2 管理，不放入 Shell 的插件目录）
  类型：

  内置扩展（随 L2 分发，在 builtin_extensions/）

  社区扩展（从包管理下载到用户扩展目录）

  规范：

  所有扩展实现统一接口 IEditorExtension / IEngineModule 等，由 L2 的 loom_plugin_loader 加载。

  依赖声明在 extension.json 中，并符合 project.json 的 required_packages。

  禁止直接引用 core/shell 或 L0 任何组件，只能通过 L2 提供的 API。

  工程级插件（L4）与 L3 对齐：

  工程 addons/ 目录下的插件也遵循相同的 IEditorExtension 接口。

  L2 加载扩展时把工程目录加入搜索路径，使其表现为“工程范围内的 L3 插件”。

  L4 · 工程（用户数据）
  位置：用户指定目录（如 ~/VitaLoom Projects/MyGame/）
  结构：

  text
  MyGame/
  ├── project.json          # 工程元数据、required_packages、disabled_plugins
  ├── scenes/
  ├── scripts/
  ├── assets/
  └── addons/               # 工程级 L3 扩展
  project.json 中的 required_packages 强制声明需要的 L3 扩展及版本。

  L2 在打开工程时检查版本兼容性，并提示安装缺失扩展。

  工程插件与 L3 使用完全相同的加载机制，只是生命周期随工程开关。

  三、发行打包目录结构
  针对开发态和发行态统一规划：

  开发态（源码树）
  text
  src/
  ├── core/shell/              # L0
  ├── plugins/shell/           # L1 内置（crash_reporter, auto_updater）
  ├── plugins/lotucosm.vitaloom.product/   # L2 大插件
  ├── extensions/              # L3 内置扩展（开发期可在此调试）
  └── tests/
  发行版（安装后目录）
  text
  /VitaLoom/
  ├── FrameCore.exe             # PyInstaller 引导程序
  ├── _internal/               # Python 运行时 + 冻结的 L0 模块
  ├── plugins/                 # 可写目录，L1、L2 插件实际放置
  │   ├── shell_crash_reporter/
  │   ├── shell_auto_updater/
  │   └── lotucosm.vitaloom.product-1.3.0/
  (或通过符号链接指向)
  ├── extensions/              # 用户级 L3 扩展（由 L2 管理）
  ├── user_data/               # 配置、日志、缓存
  └── uninstall.exe
  打包关键点：

  L0 和引导程序冻结进 _internal，不可直接修改。

  plugins/ 目录完全可写，所有 L1/L2 更新都发生在这里。

  L3 扩展由 L2 的包管理器写入 extensions/，与核心完全隔离。

  四、更新流程集成（以更新 L2 为例）
  Shell 启动，加载 L1 auto_updater。

  auto_updater 扫描 plugins/ 所有 plugin.json，得到 L2 的版本 1.2.0。

  向更新服务器查询 lotucosm.vitaloom.product 的最新稳定版 1.3.0。

  下载新版到 plugins/.cache/lotucosm.vitaloom.product-1.3.0/。

  校验完整性后，在 plugins/ 下创建新版本目录，并更新版本指针文件。

  提示用户重启，下次启动时 PluginRegistry 加载新版本 L2，旧版本保留可供回滚。

  五、关键接口定义（抽象）
  python
  # L0 暴露
  class IShell(ABC):
      def get_service(self, service_name: str): ...
      def emit_event(self, event:
  Event): ...
      def register_main_window(self, window): ...

  # L2 必须实现
  class IProductHost(ABC):
      def on_load(self, shell:
  IShell): ...
      def on_unload(self): ...

  # L3 扩展（织机专用，由 L2 定义）
  class IEditorExtension(ABC):
      def activate(self, loom_api): ...
      def deactivate(self): ...
  所有具体实现只依赖这些抽象，确保了可替换性。

  六、生命周期顺序（优化后）
  text
  Shell 启动
   -> 加载 L1 插件（按依赖拓扑）
      -> crash_reporter 最先激活
      -> auto_updater 检查更新（后台）
   -> 加载 L2 大插件（依赖 L1 完成后）
      -> L2.on_load(shell)
         -> 创建内部总线
         -> 初始化运行时
  (lotucosm)
         -> 构建 UI (hub, vitaloom)

  -> 注册主窗口到 Shell
         -> 扫描 extensions/ 和 builtin_extensions/ 加载 L3
   -> Shell 进入事件循环
   -> 用户打开工程 -> L2 加载工程，按 project.json 启用/禁用 L3 扩展
   -> 关闭时：L2.on_unload()
  -> L1 插件卸载 -> Shell 退出
  这个架构在保持原有分层优势的基础上，明确了各层的接口、更新机制与打包结构，实现了 “内核稳定、产品可替、扩展开放、更新独立” 的目标。
